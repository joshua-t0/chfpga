The CRS is a compact Ultrascale+ RfSoC FPGA board built by *t0 technologies* to implement next-generation high performance and large-density signal processing arrays. The CRS provides 8 14-bit ADC (typically used at 3200 MSPS with `chFPGA`), 8 DACs, 100G Ethernet QSFP interface, 6× 25 Gbps SFP links, high-speed 4- and 16-board backplane capability with 25 Gbps links, and clocking structure allowing deterministic synchronization of multiple boards.

Platform wrapper
================

`chFPGA` is implemented on the CRS using the `chfpga_crs` platform wrapper, which defines the CRS-specific FPGA interfaces, loads the firmware configuration parameters (see below),  and passes all of those to a `chFPGA` instance.  

See :ref:`platform_wrappers` for more details on the structure of a platform wrapper.

.. _crs_configs:

Configurations
==============

The CRS platform currently supports four `chFPGA` firmware configurations, each of which is defined as a set of constants defined in the correspondingly-named configuration package file.

 i s: ``ct`` (corner-turn with real-time offload), ``corr8``, ``corr32``, and ``corr64`` (correlator configs with increasing antenna counts). All use 8 ADC channels, 14-bit resolution, UCAP capture, and the CHORD FFT. 

- :doc:`ct (chfpga_crs_ct_config.vhd) <crs_ct_config>`: 8-channel F-Engine with CHORD FFT, 8-channel corner-turn, 100G offload with programmable packetizer; no correlator. 
- :doc:`corr8 (chfpga_crs_corr8_config.vhd) <crs_corr8_config>`: 8-channel F-Engine with CHORD FFT, 8-channel corner-turn and 8-channel :math:`N^2` correlator.
- :doc:`corr32 (chfpga_crs_corr32_config.vhd) <crs_corr32_config>`: 8-channel F-Engine with CHORD FFT, 32-channel (4 boards)  corner-turn with 32-channel :math:`N^2` correlator.
- :doc:`corr64 (chfpga_crs_corr64_config.vhd) <crs_corr64_config>`: 8-channel F-Engine with CHORD FFT, 64-channel (8 boards)  corner-turn with 64-channel :math:`N^2` correlator.

See :ref:`config_param_reference` on the structure of a configuration file.

Clocking hardware
=================

A 50 MHz oven-stabilized voltage-controlled crystal oscillator (VCXO) is the central clock source of the CRS board.
The VCXO feeds the two on-board PLLs:


- AD9574 Fixed-frequency PLL, uses the VCXO to generate fixed system clocks and provides the basic system clocks needed to boot the board, namely the FPGA's processing system (ARM cores etc.).
- HMC7044 Programmable PLL, which can 1) phase-lock the VCXO to an external 10 MHz reference clock if needed and 2) generate a number of programmable frequencies for the FPGA.


The board can operate with the VCXO not locked to an external reference.  The free-running VCXO is sufficiently accurate and stable enough to operate the system without that reference.
This allows the system to power up without the programmable PLL being configured, and allows the board to operate without external reference clock for stand-alone applications where multi-board synchnisation is not required.

The HMC7044 PLL can be configured over an SPI port connected to the FPGA's PS.  When configured, the HMC7044 can optionally phase-lock the VCXO to one of 4 sources:

  - On-board SMA Reference clock (typically 10 MHz)
  - Backplane reference clock  (typically 10 MHz)
  - Ethernet clock (125 MHz) recovered by the PHY
  - Clock generated by the FPGA (typically some recovered clock)

`chFPGA` is designed to operate with either of the first two sources.

Operating the ADCs require the following clocks:


- RF_CLK: ADC sampling clock to the ADC tiles
- PL_CLK: signal processing clock to the PL
- PL_SYSREF: Synchronization clock provided to the PL
- RF_SYSREF: Synchronization clock provided to the ADC tiles

The OSCOUT (50 MHz) and copy of the PLL SMA or backplan 10 MHz referencence clocks are also fed to the FPGA and used by `chFPGA` to implement deterministic  multiboard synchronization.

Programmable PLL Clock frequency selection
==========================================

RF_CLK
------

We originally targeted ADC sampling frequencies of 3000 MSPS, and increased this to 3200 MSPS to provide a guard band to ease the analog antialiasing filter design.
We want firmware that can operate at both frequencies. The PLL provides this sampling frequency to the ADC tiles directly, which is possible since the maximum output frequency of the PLL is 3.2 GHz. We don't use the in internal PLL in the ADC tiles to minimize additive (uncorrelated) phase noise and maximally take advantage of common-mode phase noise rejection in cross-correlation measurements. This also potentially simplifies multi-tile and multi-chip ADC synchronization.

SYSREF
------

The PLL also generates SYSREF, which must follows the following rules:

- It must be a submultiple of Fs/16
- It shall be between 0.4 and 10 MHz inclusively (see DS926 RfSoC DC and AC characteristics datasheet, table 137).
- We add the constraints that SYSREF should also be a submultiple of the 10 MHz reference clock in case we need to synchonie logic between these clock domains.

The PLL requires the divided to be an even number, but that is guaranteed if we look for a sumbmultiple of fs/16.

We look for a common submultiple frequency::

   fcommon_max = 3000/16/k1 =  3200/16/k2

By simplifying the fraction ``k1/k2``, we find the lowest integers ``k1`` and ``k2`` that will yield a common frequency, and that frequency will the the largest common frequency for both fs/16::

   k1/k2 = 15/16  => k1 = 15, k2=16
   fcommon_max = 3000/16/k1 = 3200/16/k2 = 12.5 MHz

We need to divide ``fcommon_max`` further with an integer to get below 10 MHz, but we also want this frequency to be a submultiple of 10 MHz. So::

   fsysref = fcommmon_max/k3 = 10 MHz/k4
   k3/k4 = 12.5/10  = 25/20 = 5/4, -> k3=5, k4=4
   fsysref = 12.5/k3 = 10/k4 = 2.5 MHz

The final divider factors ``k`` applie dby the PLL di divide the ADC sampling freqeny down to SYSREF are::

   fs=3000, k=3000/2.5 = 16*k1*k3 = 1200
   fs=3200, k=3200/2.5 = 16*k2*k4 = 1280

Both values of 'k' are even numbers, as required by the PLL.

PL_CLK
------

PL_CLK is simply fs/8, since we process 8 samples at a time, giving a signal processing clock of 375 or 400 MHz, which is manageable on a Ultrascale+.


SYSCLK
------

SYSCLK is used by the FPGA's MMCMs to generate internal clocks independent of the data acquisiiton and processing clocks. Those generated frequencies are used to decode IRIGB and run peripherals such as SPI, I2C, buck converter synchronization etc.

For the CRS, SYSCLK is set to 10 MHz, which is a frequency that is generated easily whether the PLL VCO is at 3000 or 3200 MHz.

SYSCLK is a PLL-generated clock that can be optionally be aligned to the external 10 MHz reference clock once the PLL Sync procedure has been performed, but SYSCLK is present whether or not such an  external reference clock is provided or not. SYSCLK can therefore also be used as a proxy for the external reference clock, or simulate one if none is provided.


FPGA port description
=====================

sma_clk10_p, bp_clk10_p
-----------------------

These are the 10 MHz reference clocks from the SMA and backplane, respectively, that are also fed to the HMC7044 PLL to phase-lock the 50 MHz VCXO. 

These clocks are used to select the proper 50 MHz edge that aligns with the 10 MHz edge in order to  align the PLL outputs.

The rising edge of the clocks are expected to be more or less aligned with the rising edges of the corresponding IRIG-B signals. 
Note that the IRIG-B signal is not necessary to synchronize the PLL outputs: any 10 MHz edge will do. But we do need to select the proper 10 MHz source.

The 10 MHz source (SMA or backplane) is selected by software using a BUFGMUX. We did not implement an automatic clock selection, partly because the PLL will do its own selection, and partly because the LVDS input lines will randomly toggle in the absence of a signal, which makes autodetection difficult. 

.. Note:: 
   
   The problem with automatic clock detection is because the clocks are AC-coupled, so no clocks mean the LVDS inputs are essentialy floating around their trigger points. There are no external pull-ups and pull-downs to force a non-zero  differential voltage. We tried using IO standard with a bias with the properties below, but that did not work well:: 

      # set_property IOSTANDARD DIFF_SSTL18_I_DCI [get_ports sma_clk10_p]
      # set_property DQS_BIAS TRUE [get_ports sma_clk10_p]

sma_irig_p/n, bp_irig_p/n
-------------------------

The IRIG-B SMA and backplane inputs are first resampled in their respective 10 MHz domains (``sma_clk10`` and ``bp_clk10``), using IOB registers clocked on the falling edge and then on the rising edge of the selected 10 MHz clock. We start with the falling edge to ensure maximum setup and hold time, as the IRIG-B signals transitions are supposed to be aligned to the rising edge of the corresponding reference clock, plus or minus some cable length and FPGA routing diffferences. 

The resulting time and trigger signals are then passed into :entity:`chfpga`, where they are further pipelined on the falling and then rising edge of the 200 MHz ``clk200`` clock. ``clk200`` is derived from ``clk10``, which comes from the programmable PLL and is aligned with the external reference clock once the PLL synchronization process is complete.



Synchronization
===============

The CRS provides the signals to the FPGA allowing for both multi-tile and multi-board synchronization.


Top-level time and trigger ports
================================

The CRS platform wrapper :entity:`chfpga_crs` exposes the following timing-related ports:

* ``sma_irig_p/n`` — differential IRIG-B input from the front-panel SMA.
* ``bp_irig_p/n`` — differential IRIG-B input from the backplane.

Inside :entity:`chfpga_crs`, each IRIG-B input is first converted to single-ended form using an ``IBUFDS`` and then resampled in its **own** 10 MHz reference clock domain:

* ``sma_irig_p/n`` is resampled in the ``sma_clk10`` domain.
* ``bp_irig_p/n`` is resampled in the ``bp_clk10`` domain.

In both cases the resampling is done with two flip-flops clocked by the 10 MHz reference: one on the **falling edge**, then one on the **rising edge**. The first register is implemented in the IOB to guarantee reproducible input timing. The resampled signals are then combined into the ``time_trig(0 to 1)`` vector that is passed to :entity:`chfpga`:

* ``time_trig(0)`` — backplane time / IRIG-B signal used by the system logic.
* ``time_trig(1)`` — backplane trigger signal.

Within :entity:`chfpga` and :entity:`system`, this vector is further pipelined on the rising edge of the 200 MHz ``clk200`` clock before being presented to the IRIG-B decoder, time-tagging logic and reference-clock synchronization state machines. This double registration (in 10 MHz and then in 200 MHz) ensures deterministic and well-characterised timing for all time/trigger events across the system. To guarantee this, ``clk200`` must be generated from a clock source that is synchronous to the external time/trigger domain used to drive ``time_trig``.

PLL Synchronization
-------------------

PLL synchronization consists in aligning the ADC sampling and processing clocks to the external 10 MHz reference clock in order to ensure that the first sample of every frame is taken at a deterministic (fixed) delay after the 10 MHz external reference clock edge.

When the PLL is locked to the external reference, the 50 MHz VCXO edge, which is provided to the FPGA by OSCOUT, is mostly aligned to the external reference clock edge.

The PLL_SYNC signal needs ot be synchronous with the VCXO, and must provide adequate setup and hold times to that clock. Once PLL_SYNC is set, that signal is captured on the next rising edge of the VCXO, and the rising edge of the PLL outputs dividers will be aligned to the following rising edge of the VCXO.

A PLL_SYNC event is initiated by software by setting a control line on a BSB register, which is first aligned to a rising edge of the 10 MHz reference clock using a CDC clock. That 10 MHz edge is captured on the *falling* edge of 50 MHz OSCOUT to ensure maximum setup and hold time between those two edges. This provides maximum resilience to small phase alignment betreen OSCOUT and the reference clock. The captured edge is further delayed by 3 additional *falling* edges of OSCOUT, and is then sent out to the PLL to be captured by the next *rising* edge of the VCXO. Here again, the edge switching ensures maximal setup and hold time in case of misalignment tof OSCOUT and VCXO. The SYNC signal is captured on the next rising edge of VCXO, and the divider outputs restart their waveforms on the following rising edge of VCXO.  At that point, the PLL outputs should be aligned to the 10 MHz external reference clock.

ADC Synchronization
-------------------

The ADC synchronization consists in adjusting the ADC sampling clock delays in order to ensure deterministic capture of the ADC data and to set the data latency through the ADC internal logic to a known value used by all ADCs on all boards.

Array synchronization
---------------------

Array (i.e multi-board)  synchronization is performed using the IRIG-B signal.

- Each board continuously decode the IRIG-B time and interpolates the intra-second time down to a resolution of 10 ns.
- The host computer sets a future SYNC trigger time by setting a target IRIG-B time on every board. That time should be close to the *falling* edge of a 10 MHz clock.
- Once the boards detect the target time, they start the SYNC process on the next *rising* edge of the reference clock. The edge reversal is used to allow maximum setup/hold time.
- ADC Data framing restarts a fixed number of reference clock and/or signal processing clocks after the SYNC process has been triggered, therby ensuring every ADC bof every board starts sampling at the same time.

This process is relatively simple if the IRIG-B signal is synchronous to the refernece clock (e.g. both are generated by the same GPS receiver unit). In that case, the IRIG-B trigger is simply set a fixed offset from the current time, making sur eto round off and offset the subseconds to align the trigger to the falling edge of the reference clock. An additional delay tweak of multiples of the reference clock can be introduced to ensure that the ADC frame will end up being aligned with the IRIG-B second.

If the reference clock is not synchronous to the IRIG-B signal (e.g. reference clock is provided by a hydrogen MASER, and IRIG-B is form a GPS receiver), the software will need to track the drift between the IRIG-B and the reference clock, and anticipate the extra offset needed to set a  IRIG-B trigger that will be close to the falling edge of the reference clock. This requires the drift between the two signal to be slow enough and predictible enough to allow relative timing of the trigger within +/-50 ns.



Constraint files
================

- ``crs_timing_constraints_common.xdc`` — Shared by all CRS configs: operating conditions, clock periods (SMA 10 MHz, backplane refclk, OSCOUT, PL_CLK, SYS_CLK, etc.), input/output delays, multicycle paths, and clock groups.
- ``crs_physical_constraints_common.xdc`` — Shared by all CRS configs: I/O pin assignments (SMA 10 MHz, backplane refclk, PLL, PL_CLK, SYSREF, SYS_CLK, IRIG-B, buck sync, etc.) and other physical settings.
- ``crs_physical_constraints_chord_fft_LOCs.xdc`` — CHAN PFB/FFT LOC constraints (fft_wideband_real BRAMs for CHAN[0]–CHAN[7]).
- ``crs_physical_constraints_chan_LOCs.xdc`` — CHAN UCAP, SCALER and FUNCGEN LOC constraints (URAM, BRAMs, DSPs for CHAN[0]–CHAN[7]).
- ``crs_physical_constraints_ct.xdc`` — ct config only: QSFP/100G Ethernet pins, 156.25 MHz CGE refclk, and floorplanning for the CGE (UPACK+CGE) block.
- ``crs_physical_constraints_corr.xdc`` — corr8 config: corner-turn (CORN) pblock only.
- ``crs_physical_constraints_ucorr44_8_LOCs.xdc`` — corr8 config: CORR pblock and URAM/DSP LOCs for ucorr44 correlator.
- ``crs_physical_constraints_corr64.xdc`` — corr32 and corr64 configs: backplane GTY refclk, CORN pblock, ALIGN1 FIFO LOCs.
- ``crs_physical_constraints_ucorr44_64_LOCs.xdc`` — corr32 and corr64 configs: CORR pblock and URAM/DSP LOCs for ucorr44 correlator.


Timing constraints
------------------

Timing constraints (clock periods, delays, multicycle paths, and clock groups) are defined in ``crs_timing_constraints_common.xdc`` and are included in all CRS builds. The physical constraint files only define I/O and placement.


Physical Constraints / Floorplanning
------------------------------------

We originally exclusively used PBLOCKs to constrain the placement of each submodule in `chFPGA`. This would often lead to unreliable timing results despite this tight guidance. VIvado 2022.2 would randomly fail to meet timing even if insignificant changes were made. We even used a python script to automatically generate sub-Pblocks for the FFT, FFB, SCALER, FUNCGEN, but to no avail

We reverted to using AI to analyze the structure of the code base and create a LOC constraint for each DSP48 and RAMB primitives of the correlator and each RAMB resources of the other large submodules, especially the FFT. This approach has proven to be much more reliable and robust, and yields shoter build time.

On the CRS, the general flow of the data is from right to left; The ADCs are on the right side, and the GTYs or ARM cores are on the left for data offload. The single column of UltraRAM is also on the left side, which is convenient since they are used by the post-channelizer logic (correlators, corner-turn engine, data capture engine).
